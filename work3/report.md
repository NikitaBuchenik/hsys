## ВВЕДЕНИЕ

Цель работы — закрепить навыки программирования CUDA, изучить использование разделяемой памяти при умножении матриц и сравнить оптимизированный алгоритм с наивной реализацией.

Разработаны шаблонные классы `Data`, `MatrixView` и `Matrix`. Реализовано ядро `kernel_matmul_shmem`, использующее разделяемую память для повторного применения фрагментов входных матриц. Представление `MatrixView` передаётся в ядро по значению. Оператор `operator*` использует стратегию `SharedMemory`, а наивный вариант сохранён для сравнительного эксперимента.

Корректность проверяется по эталонному произведению Eigen для 343 комбинаций размеров. Производительность исследуется для квадратных матриц порядков 16, 32, 64, 128, 256, 512 и 1024.

Исходный код, тестовый протокол и результаты: https://github.com/NikitaBuchenik/hsys/tree/main/work3

## 1 Разработка программного решения

### 1.1 Владение памятью: Data

Класс `Data` владеет массивом в глобальной памяти GPU. Выделение выполняется через `cudaMalloc`, освобождение — через `cudaFree`. Копирование выполняет глубокую копию устройства в устройство; перемещение передаёт указатель. При расчёте размера проверяется переполнение, а ошибки вызовов CUDA обрабатываются через `CUDA_CHECK`.

### 1.2 Представление MatrixView

`MatrixView` хранит невладеющий указатель, число строк и число столбцов. Элемент `(i, j)` располагается по индексу (i\cdot ncols+j), то есть используется построчное хранение (row-major). Представление не управляет временем жизни памяти и передаётся в CUDA-ядро по значению. Для входных данных применяется `MatrixView<const T>`, чтобы запретить изменение элементов через входной интерфейс.

### 1.3 Оператор умножения и стратегия

Перед запуском проверяется совместимость размеров: число столбцов первой матрицы должно совпадать с числом строк второй. Затем создаётся матрица результата и выбирается реализация. `operator*` использует `MatmulStrategy::SharedMemory`; функция `multiply_naive` позволяет запускать исходный наивный алгоритм для сравнения. После запуска ядра вызывается `cudaDeviceSynchronize`, чтобы дождаться выполнения и обнаружить ошибки.

### 1.4 CUDA-ядро с разделяемой памятью

Блок содержит (16\times16=256) нитей и вычисляет плитку результата размером 16×16. На каждой итерации потоки загружают фрагменты матриц A и B в две плитки shared memory. Если индекс выходит за границы входа, вместо элемента записывается ноль. После загрузки выполняется `__syncthreads()`; затем каждая нить накапливает частичную сумму. Вторая синхронизация гарантирует, что плитки больше не читаются перед перезаписью на следующей итерации.

Такой подход уменьшает повторные обращения к глобальной памяти за счёт повторного использования загруженных значений. При этом добавляются затраты на загрузку плиток и синхронизацию, поэтому ускорение зависит от размера матриц и архитектуры GPU. Размеры, не кратные 16, обрабатываются за счёт проверки границ и нулевого заполнения.

Для матриц (A_{m\times k}) и (B_{k\times n}) вычислительная сложность составляет (Theta(mkn)). Для квадратных матриц это (Theta(n^3)). Использование shared memory улучшает повторное использование данных, но не меняет асимптотическую сложность.

## 2 Модульное тестирование

Google Test формирует декартово произведение трёх наборов размеров ({1,2,3,127,128,129,512}), то есть (7^3=343) сочетания для (m,k,n). Эталон рассчитывается с помощью Eigen. Результат сравнивается через `isApprox` с допуском (10^{-5}); дополнительно проверяется максимальная абсолютная погрешность не более (10^{-5}).

Сохранённый `results/tests.xml` содержит 347 тестов, 0 ошибок и 0 падений. В параметризованной группе присутствуют все 343 сочетания размеров. Остальные тесты проверяют некратные размеру плитки размеры, несовместимые матрицы, нулевое внутреннее измерение и согласованность наивной и shared-memory реализаций.

## 3 Методика измерения производительности

Измерения выполнялись Google Benchmark в Release-сборке. Для каждого размера в сохранённом наборе есть пять повторений для обеих реализаций; в таблице используются медианные значения. Входные матрицы выделяются и копируются на GPU до измеряемого интервала. CUDA Events измеряют вычисление ядра, не включая выделение памяти результата и освобождение памяти. Следовательно, полученные значения характеризуют вычислительную часть, а не полное время приложения с передачей данных между CPU и GPU.

Среда измерения по сохранённым файлам: NVIDIA GeForce RTX 2060, 6144 МиБ памяти GPU; CUDA Compiler 13.0.88; драйвер NVIDIA 595.79; в выводе `nvidia-smi` указана CUDA Version 13.2; Google Benchmark v1.9.1, Release. В метаданных benchmark указаны 12 логических процессоров и частота 3793 МГц.

### 4.1 Анализ графиков

Графики `results/complexity.png` и `results/speedup.png` построены по сохранённым результатам benchmark. На размерах 16 и 32 наивное ядро быстрее: затраты на загрузку плиток и синхронизацию не окупаются при небольшом количестве вычислений. Для размеров 64 и 128 выигрыш невелик — около 4 % и 3 %. При размере 256 ускорение составляет 1,216 раза, при 512 — 1,263 раза, а при 1024 — 1,292 раза. В данном эксперименте максимальный выигрыш составляет около 29 %.

### 4.2 Сопоставление с теоретической сложностью

Теоретическая сложность умножения квадратных матриц — (Theta(n^3)). При удвоении (n) ожидаемое число операций возрастает примерно в восемь раз. Для shared-memory ядра измеренное время увеличивается примерно в 6,69 раза на интервале 256→512 и в 7,84 раза на интервале 512→1024. Для наивного ядра соответствующие отношения составляют около 6,95 и 8,02. На крупных размерах наблюдения согласуются с кубической моделью.

На малых размерах время не обязано расти монотонно: затраты на запуск ядра и измерение могут быть сопоставимы с полезными вычислениями. Также на результаты влияют планирование блоков, пропускная способность памяти, синхронизация и состояние GPU. Полученные результаты относятся к указанной конфигурации и не являются универсальной гарантией ускорения.

## 5 Вывод

Реализовано умножение матриц с использованием разделяемой памяти CUDA, плиток 16×16 и синхронизации `__syncthreads()`. Сохранённый протокол содержит 347 успешно завершённых тестов, включая все 343 заданные комбинации размеров. На NVIDIA GeForce RTX 2060 shared-memory реализация уступает наивной для самых маленьких размеров, однако при (n=1024) показывает ускорение около 1,292 раза. Измерения на крупных размерах в целом согласуются с теоретической вычислительной сложностью (Theta(n^3)).
