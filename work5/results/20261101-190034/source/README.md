# Работа 5 — параллельная редукция вектора

Два CUDA-кернела вычисляют сумму всех элементов `float`-вектора:
`kernel_vecred_nobr` — дерево в shared memory;
`kernel_vecred_br` — обмен регистрами через `__shfl_down_sync` и shared memory для сумм варпов.
Код подготовлен для Windows x64, CUDA и NVIDIA GPU. Здесь нет доступной GPU для сборки
и запуска: окончательная проверка выполняется на втором ПК. Результаты не придуманы;
папка `results` появится только после настоящего запуска.

## Запуск на нашем ПК с RTX 2060

Уже установленные для работы 4 CUDA Toolkit, VS 2022 Build Tools с MSVC 14.39,
CMake, Ninja, Git и Python 3.9.4 подходят. Переустанавливать их не нужно.
В **cmd**, по одной строке:

```bat
cd /d H:\hsys
git pull --ff-only
cd work5
build.cmd
run.cmd
report.cmd
```

В PowerShell используйте `cd H:\hsys`, затем `git pull --ff-only`, `cd work5`,
` .\build.cmd`, ` .\run.cmd`, ` .\report.cmd` (без пробела перед точкой).
Следующую команду запускайте только после успеха предыдущей.

`build.cmd` находит уже настроенный компилятор, прежний каталог `H:\BuildTools2022`
либо VS 2022 через `vswhere`. Пути с пробелами заключены в кавычки. Архитектура GPU
определяется CMake автоматически (`native`), поэтому скрипт не привязан к RTX 2060.
При необходимости: `build.cmd -Architecture 75` для RTX 2060 или
`build.cmd -Architecture 89` для RTX 4070. На другом ПК необходимо установить
совместимые CUDA Toolkit, MSVC 14.39, Windows SDK и компонент C++ CMake tools.
Первый запуск CMake скачивает Google Test 1.15.2, Google Benchmark 1.9.1 и Eigen 3.4.0.
Тесты с Eigen собираются как обычный C++, а не CUDA: ошибка Eigen `::arg` из работы 4 не повторяется.

`run.cmd` сначала выполняет **24 теста**, затем **2 алгоритма × 29 размеров × 5 повторов**.
Закройте игры и тяжёлые GPU-приложения; не запускайте два эксперимента одновременно.
Большие размеры передают много данных между CPU и GPU, поэтому весь запуск может занять
заметно больше времени, чем сумма напечатанных CUDA-времён. Не прерывайте его ради маленьких значений в таблице.
Успех — строка `SUCCESS`. При ошибке бенчмарки/отчёт не объявляются корректными.

`report.cmd` устанавливает только Python-пакеты из `scripts/requirements.txt`, проверяет
полноту данных, строит графики и DOCX, затем обновляет ZIP. Успех — `REPORT SUCCESS`.
Версии пакетов совместимы с Python 3.9.4. В отчёте стоят прежние авторы и группа;
перед сдачей нужно проверить титульник и окончательное оформление по СТУ 7.5–07–2021.

Результаты находятся в `results/YYYYMMDD-HHMMSS`, ZIP — рядом. Путь последнего успешного
запуска записан в `results/latest.txt`. В комплект входят XML тестов, JSON всех повторов,
CSV, графики `complexity.png`, `speedup.png`, `report.docx`, версии оборудования/компилятора,
Git-хеш и снимок исходников с SHA-256. Старые запуски не перезаписываются.

## Почему большие векторы обрабатываются частями

В задании **число элементов**, а не байтов: `n = 8 * 2^e`, `e = 0..28`.
Максимум — **2 147 483 648 элементов**, то есть **8 ГиБ FP32**. На RTX 2060 с 6 ГиБ
такой вход целиком не помещается. По согласованию большие входы обрабатываются частями,
без сокращения диапазона размеров и без экстраполяции времени.

- Входной GPU-буфер — до 256 МиБ (не больше четверти свободной GPU-памяти при старте).
- `resident`: весь вход помещается в этот буфер, загружается один раз перед замерами.
- `streamed`: обрабатываются все части полного логического вектора, каждая загружается
  до своего CUDA Events-интервала. Суммы частей хранятся на GPU, финальная редукция
  этих сумм также входит в время.
- Время `streamed` — **сумма вычислительных интервалов**, а не полное время с PCIe.
  Копирование исключено по заданию, однако может влиять на кеши между интервалами.
  Оба алгоритма получают одинаковую схему обработки; режимы разделены на графиках.

Весь логический вход задаётся `x[i] = ((i % 257) - 128) / 256`. Полный период имеет
нулевую сумму; остаток позволяет независимо проверить ответ аналитически. Это настоящая
обработка всех n элементов, а не повторный замер одной части с умножением времени.
На CPU хранится только шаблон одной части с небольшим запасом, а не 8 ГиБ данных.
Не следует переносить выводы о численной ошибке на произвольные входы.

## Алгоритмы и синхронизация

Блок — 256 нитей, до 512 элементов. Каждая нить читает до двух элементов; хвост
заменяется нулями, никто не выходит до барьеров. Загрузка одинакова у обоих вариантов.

В `nobr` (без обмена регистрами) 256 частичных сумм находятся в shared memory;
шаг дерева уменьшается 128, 64, ..., 1. Каждый шаг заканчивается `__syncthreads`.
Название не означает «вообще без ветвлений»: условия для хвостов и дерева присутствуют.
Shared memory: 1024 байта, 9 барьеров блока с учётом начального.

В `br` каждый из восьми полных варпов выполняет пять shuffle-шагов 16, 8, 4, 2, 1.
В shared memory записываются только 8 сумм варпов (32 байта), затем выполняется один
барьер блока. Первый полный варп сворачивает 8 сумм и 24 нуля. Маска `0xffffffff`
корректна: во всех вызовах участвуют все 32 нити соответствующего варпа.
Shuffle не является барьером shared memory для всего блока.

Блоки записывают независимые суммы в глобальный буфер. Отдельные проходы того же
алгоритма уменьшают число сумм до одной. Это необходимо: shared memory одного блока
не видна другим блокам, а обычный кернел не предоставляет общий барьер всей сетки.
Время всех проходов включено. Атомики и суммирование ответа на CPU не используются.

Объём работы обоих алгоритмов — O(n); глубина дерева логарифмическая. Это не означает
O(log n) времени на реальной GPU с конечным числом исполнительных устройств.

## Тесты и измерения

16 параметризованных тестов: оба алгоритма и все восемь размеров задания
`1, 2, 3, 127, 129, 512, 541, 1037`. В каждом пять наборов данных, включая случайные
дроби. Эталон — `Eigen::Matrix::sum`, проверка — `EXPECT_NEAR(..., 1e-4)`.
Ещё 8 тестов покрывают пустой вход, границы варпов/блоков, три прохода, части с хвостом,
повторное использование памяти, неверные аргументы, move и overflow.

В бенчмарке 3 прогрева, 5 повторов, минимум 0,05 с измеренного времени на повтор.
CUDA Events стоят вокруг редукции, `UseManualTime` получает время в секундах.
GPU-память, рабочие буферы и события создаются вне интервалов. На каждом размере
ответ проверяется до и после измеряемого цикла. Ошибки, пропуски, отсутствие любого
размера/повтора или изменённые снимки исходников блокируют генерацию отчёта.
Ускорение = медиана Shared / медиана Shuffle. Полосы — min/max, не доверительный интервал.
Маленькая разница с перекрывающимися диапазонами не объявляется убедительным выигрышем.

## Файлы

- `core/include/vector.cuh`: невладеющий VectorView и владеющий DeviceBuffer.
- `core/include/reduction.cuh`, `core/src/reduction.cu`: два кернела и полный многошаговый вызов.
- `tests/vector_tests.cpp`: Eigen и Google Test на CPU, вызовы CUDA через библиотеку.
- `benchmarks/vector_benchmark.cpp`: Google Benchmark, контроль ответов и обработка частями.
- `scripts`: сборка, сбор доказательств, проверка, графики и генератор отчёта.

Опциональная проверка гонок и памяти, если установлен Compute Sanitizer:

```bat
compute-sanitizer --tool memcheck --leak-check full build\bin\vector_tests.exe
compute-sanitizer --tool synccheck build\bin\vector_tests.exe
compute-sanitizer --tool racecheck build\bin\vector_tests.exe
```

Не выполнять профилирование одновременно с бенчмарками.

После проверки результатов можно загрузить конкретную папку запуска из cmd:

```bat
set /p RUN=<results\latest.txt
git add -f "%RUN%"
git diff --cached --stat
git commit -m "Add work5 GPU experiment and report"
git push origin main
```
